# EasyPost TEST credential authorization

This service prepares TEST quote authorization. It adds no provider calls, quote routes, browser approval control, or production enablement. An operator must separately obtain the owner-approved test-key workflow evidence before calling the internal approval setter; the service does not inspect a real key to determine its mode.

EasyPost nonblank credential saves atomically write the encrypted namespaced API key, a new UUID `credentialGenerationId`, and empty `approvedTestGenerationId`. Omitted/blank credential fields remain unchanged. Existing credentials have no implicit approval. `approveEasyPostTestGeneration(database, expectedGeneration)` locks and compares the current generation, requires test mode, then records approval. A stale approval cannot approve a replacement key. Approval may precede activation; claims still require active and test mode.

The entire `ecommerce_shipping_provider_easypost__` prefix is reserved from generic settings PUT/DELETE, including category moves and future metadata fields. The dedicated setup API accepts only registry credential fields and cannot set approval/generation. Other providers retain their existing behavior. There is no arbitrary batch/import settings endpoint; specialized settings writers use fixed keys. Legacy generic `apiKey` is outside this guard and never used for quote authorization.

`lockEasyPostCredentialAuthorization(tx)` acquires transaction advisory lock `core:ecommerce:shipping:easypost:credential-authorization:v1`. Rotation, approval, provider configuration and caller-owned claim/recheck transactions share it. Consumers must acquire this lock before their quote claim locks and retain it until the database claim transaction commits. `readAuthorizedEasyPostTestCredentials(tx)` and `recheckEasyPostTestGeneration(tx, expectedGeneration)` return exactly `{provider:'easypost', mode:'test', apiKey, credentialGenerationId, approvedCredentialGenerationId}`. Never log or publicly serialize this transport snapshot.

Authorization reads query matching-category settings and provider rows directly through the supplied transaction; they never use the setup helper's cache or legacy fallback. Keys must have `isSecret=true`, valid ciphertext, nonblank plaintext, and valid generation metadata with equal approval. Strict decryption reuses the existing encryption format; generic settings decryption retains its historical fallback behavior. This is not a cryptographic format upgrade.

`readEasyPostQuoteAuthorizationReadiness(tx)` exposes only implemented/configured/approvedTestCredentials/enabled/mode/reasonCode. Missing or invalid stored configuration yields `not_configured`; unavailable database/lock reads throw sanitized `authorization_unavailable` and must become a 503, not a false configuration status. Known claim denials are `credentials_unapproved`, `credential_generation_changed`, `provider_inactive`, `provider_not_test`, and `credential_configuration_invalid`. Unexpected errors carry no raw database cause or submitted key. Standalone write failures use `credential_write_failed`.

An already-claimed operation can retain its captured generation. A separate pre-dispatch recheck detects committed rotation/deactivation, but cannot make a database check atomic with external HTTP I/O. Future orchestration must preserve that boundary and the approved quote retry contract.

Retire all old EasyPost configuration writers before claiming complete generation enforcement: old application instances and direct SQL can bypass the new service lock/metadata rules. Previously overwritten legacy credentials cannot be reconstructed. This patch performs no production migration, approval, or key rotation. Canonical settings caches are invalidated only after successful writes; claim correctness does not depend on cache freshness.

Validation uses synthetic credentials and disposable loopback PostgreSQL only. The opt-in suite requires `SHIPPING_AUTHORIZATION_TEST_DATABASE_URL` with exact database `core_shipping_authorization_test`; retained isolation tests use their separate database. Cases cover atomic rollback, stale approval, locked concurrent claims/rotation/deactivation, uncached reads, malformed storage, public readiness, and absence of implicit legacy approval. Mounted route tests cover generic namespace denial, caller metadata rejection, unchanged auth/module gates and public response redaction.
