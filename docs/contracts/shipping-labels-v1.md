# Shipping labels v1 — approved implementation direction

Status: Orchestrator-approved implementation direction, 2026-09-07 UTC. This governs a separate development branch from frozen ece2544. It authorizes implementation and synthetic validation, not actual provider calls or production deployment.

Orchestrator decisions: implement separate label-specific activation and generation-bound approval, durable purchase claims, generation-independent shipment uniqueness, and allocation-aware quantity validation. Explicit dispatch conversion is included in the program milestone and must reuse the existing atomic fulfillment/outbox behavior. Purchase alone must never create fulfillment or notification work. Recovery after credential rotation requires a separate audited recovery-only binding; do not retain old secrets implicitly. Retain unresolved private snapshots; redact 30 days after terminal operational resolution, with backup retention documented separately. Refund/void and production activation remain visible subsequent work, not claims of completed ecommerce.

The first implementation slice is strict shared request validation and pure lifecycle policy, followed by additive persistence and allocation concurrency. Before persistence code, publish the exact transaction API, table constraints and migration ordering for review. Audit every fulfillment writer before integration. Transport, asset retrieval, UI and dispatch integration follow after their contracts and failure cases are reviewed. New label asset downloads remain disabled until an exact HTTPS-origin policy is approved from provider evidence; generic HTTPS/S3 allowlists are forbidden.

The sections below retain the proposal's rationale and clearly distinguish external documentation from Core policy. Statements labeled proposed are approved directions subject to the concrete interface review above; they do not delegate architectural discretion to individual workers.

## Established facts and limits

**Current Core source:** `docs/contracts/shipping-quotes-v1.md` authorizes domestic US states/DC, USD, test-only quotes. Quote attempts retain internal shipment/rate/account IDs and a credential generation, but public projection intentionally omits shipment/account identity. Current readiness approves quotes, not purchases. `shared/schema/ecommerce-shipping-quotes.ts` scopes provider shipment uniqueness by generation. `ecommerce-shipping-credential-authorization.service.ts` replaces the encrypted key and clears approval atomically; it does not retain historical keys or establish a stable external account identity. `ecommerce-shipping-quote-orchestration.ts` redacts terminal snapshots after 30 days. Label methods in `ecommerce-shipping-carrier.service.ts` are placeholders. Existing fulfillment rows have optional label fields, but the fulfillment path changes fulfillment state and queues notifications; those rows are not a durable label-purchase journal.

**Primary provider facts:** EasyPost buys an existing shipment using its selected rate ID; purchased responses include postage and tracking information. Exact shipment retrieval is available. Its examples expose selected-rate and fee information. The documented buy parameters contain no merchant-supplied maximum-charge condition. These facts do not establish an atomic price guarantee or a general idempotency-header guarantee. [Shipment API](https://docs.easypost.com/docs/shipments)

The error guide distinguishes already-purchased, purchase-in-progress and purchase timeout/no-response outcomes. Its general retry advice is not sufficient evidence for Core to repeat a potentially charged operation automatically. [Errors guide](https://docs.easypost.com/guides/errors-guide)

Postage refund is a separate endpoint with asynchronous statuses, including submitted, refunded, rejected and not_applicable. Eligibility and time windows vary by carrier; submitting a refund is not confirmation of a refund or of label cancellation. [Shipping refund API](https://docs.easypost.com/docs/shipments/shipping-refund)

The decisions below are **approved Core policy**, including states, locks, uniqueness, authorization, retention and UI behavior, subject to the concrete interface reviews stated above. No actual EasyPost account/label acceptance has occurred. Public docs reviewed did not establish general buy idempotency-header semantics, a guaranteed final-negative retrieval window, or a guaranteed all-in spending cap. Do not infer those guarantees from references, rate IDs or current error messages.

## Bounded first slice

Add explicit **test label purchase**, retrieval and unknown-outcome recovery for an already-quoted single parcel. No automatic purchase after quote, checkout, payment or scheduled job. Keep US states/DC and USD restrictions; no insurance, return labels, customs, one-call buy, batches, automatic cheapest-rate choice, production purchases or customer-facing dispatch notification in this slice.

Use a distinct default-off operator activation for label purchases and an operation-specific test-approval record bound to the credential generation. Existing quote approval and provider testMode alone must not activate buying. The UI must say “Buy test label” and show the full confirmed selection; production activation needs a later approved contract and real account/cost acceptance. A disabled feature can reject new mutations while a separately authorized operator recovery path remains available to resolve historical unknown outcomes.

## Authoritative identity and explicit cost confirmation

Approved POST body: `{version:1, quoteAttemptId, rateId, confirmedRateAmount, currency:'USD'}` with an independent UUID Idempotency-Key. Order identity comes from the route. Both IDs are opaque nonempty strings of at most 128 characters, matching the existing quote projection; quote attempt IDs are not integers. The amount is an integer-cent acknowledgement between 0 and 2147483647 inclusive, matching stored quote cents, never authority to set a price. Parsing is strict and does not coerce values. Strictly reject extra shipment/account/URL/address/credential fields. Hash only the canonical parsed client request and version; replay that request before current eligibility checks. A changed request under the same key is 409.

Resolve the immutable internal quote row under locks. Require quoted/test, same order, not expired or redacted, matching current server snapshot and credential generation, one rate belonging to that quote's exact provider shipment/account, and confirmed amount equal to the stored rate's USD cents. Resolve origin, item ownership, remaining quantities and fraud/payment/order eligibility from locked server rows, never browser state. Copy a minimal purchase-specific immutable snapshot/hash before quote retention can redact its source.

Do not reuse the existing `ShippingLabelPurchaseRequest` carrier interface as an admin request: it extends the client-address rate request, and its purchase result permits optional provider shipment identity/raw data. The new admin contract must resolve the stored quote and opaque selected rate on the server, require provider identity internally, and pass through a separate safe public projection. Existing `labelUrl`/`labelCost` fulfillment fields are eventual dispatch linkage, not justification to create fulfillment when buying.

The confirmation should show carrier/service, parcel, origin/destination summary, selected quantity, test mode, rate amount and the distinction between quoted postage and later adjustments/fees. Do not call confirmedRateAmount a guaranteed all-in cost cap. Before first buy, retrieve the same shipment and require matching shipment/mode, address/parcel identity and selected rate/account/currency/amount. A changed/missing rate or stale local input requires a new quote and new explicit confirmation, without buying. This preflight still leaves a race before provider purchase; production must remain blocked until the account's actual billing/adjustment policy and acceptable consent wording are approved.

After dispatch, never discard evidence merely because returned fees or selected-rate amount differ. Record that a purchase was observed, flag a billing discrepancy for review, prevent automatic dispatch, and do not retry or silently overwrite the confirmed price. Distinguish confirmed postage, observed selected postage, normalized fee entries and an unresolved/unknown final total; do not invent a single exact financial total from missing fields.

## Durable claims, item allocations and lock order

Propose separate purchase records, append-only operation/audit events, and item allocations; no migration number is allocated yet. Purchase fields include order/request/version/hash, quote ID/hash, provider shipment/rate/account, credential generation and expected/observed mode, confirmed cents, actor/time, private snapshot, lease/fence, dispatch-intent time, state, observed postage/tracking identity, safe result codes and reconciliation history. No credentials or raw provider bodies belong in these records.

Uniqueness must prevent another purchase of the same provider shipment even after local credential rotation. Do not copy quote uniqueness `(provider,generation,shipment)` into the purchase invariant. For this single-provider test-only slice, conservatively unique `(provider,mode,providerShipmentId)` plus `(orderId,requestKey)`; a cross-account collision fails closed. Future multi-account scoping needs verified stable account identity rather than a settings row or random generation token.

Different quotes can cover the same items. Therefore shipment uniqueness alone does not prevent duplicate labels for overlapping units. Under the order lock, reserve a **shipping allocation** against selected unfulfilled quantities while a purchase is claimed, dispatched/unknown, purchased or awaiting confirmed void. This is not an inventory reservation or fulfillment: payment already owns inventory semantics. All existing manual/automated fulfillment writes must honor or atomically consume the allocation, or they could ship reserved units and leave a second label purchase possible. This necessary cross-path change is approved in principle, with its concrete transaction API still requiring Orchestrator review before implementation; an isolated purchase endpoint cannot truthfully claim complete quantity correctness without it.

Global order: credential authorization lock → order row → location row → quote/purchase/allocation rows in stable ID order. Every purchase, dispatch conversion, reconciliation completion and void/allocation-release path must follow a reviewed compatible order. No external I/O while holding these database locks. A transaction claims once, copies the snapshot and allocation, then commits. An additional fenced compare-and-set durably records dispatch intent immediately before buy. The provider call is permitted only if that transition committed successfully; a lost commit acknowledgement produces uncertainty and no blind dispatch/retry.

Proposed states: `claimed` → `dispatching` → `purchased | unknown | rejected`; also `cancelled_before_dispatch` for a provably unconsumed claim. Lease expiry before durable dispatch intent may cancel with a CAS that prevents the old owner from subsequently dispatching. Once intent exists, timeout, interruption, malformed/mismatched/oversize response, provider-in-progress or uncertain database completion becomes `unknown`. Do not treat broad 4xx/5xx classes as proof of no purchase. Only specifically documented and tested terminal rejection codes may become `rejected`; otherwise retain uncertainty. Fenced late responses can resolve their own unresolved operation, never overwrite a purchased/rejected terminal record. Local key uniqueness does not prove exactly-once external delivery.

## Same-shipment reconciliation; no blind rebuy

Same-key POST returns the stored state and never reissues buy. New keys cannot bypass the existing provider-shipment or item-allocation claim. A GET endpoint for purchase state is local and side-effect-free. A separate authorized reconciliation action claims a bounded GET-only operation against the stored shipment ID; a bounded maintenance worker may perform the same read-only provider action if approved. It must never create a new shipment, rerate, buy or refund implicitly.

Strictly verify retrieved shipment and test mode, purchased postage identity, selected rate and carrier account, and normalized tracking/label metadata. Match accepted input identity using an explicitly reviewed normalization policy (do not compare unnormalized formatting, and do not silently accept a different address). Persist observed purchase even if a usable label asset is temporarily missing, with separate `asset_unavailable`/review status; missing download bytes do not authorize rebuy. A verified existing label with unexpected selected rate or input binding is a conflict/manual-review outcome, not permission to overwrite identity or try another purchase.

A retrieval showing no postage, or 404/401/403, cannot alone prove that a previous buy cannot still finish or that the correct historical account is accessible. Retain `unknown` and its allocation. “Already purchased” triggers retrieval of this exact shipment, not a new shipment. “In progress” remains unresolved with bounded GET backoff. For v1, after any possibly dispatched buy, **no repeat buy is exposed** until a separately approved recovery procedure establishes terminal non-purchase using provider-supported evidence. A user clicking “New quote” is not such evidence. Read-only reconciliation can retry with backoff; purchase dispatch cannot.

Credential rotation/deactivation blocks new purchase claims and known pre-dispatch changes. Captured credentials may still complete an already authorized bounded call; no check eliminates the post-check I/O race. Historical recovery cannot silently use arbitrary new credentials. Minimum safe policy is recovery blocked with an explicit credential-rebinding state after generation change. A separately audited recovery-only binding may authorize the current generation after the operator verifies account continuity and exact GET identity; it grants no buy permission. Do not add historical secret retention merely to avoid this gate, and do not relabel old results as created by the new generation.

## Label access, dispatch, refunds and retention

Keep label metadata private and no-store; label URLs may themselves be bearer access to address data. Never accept browser-supplied URLs or fetch arbitrary provider-returned hosts. Before download implementation, approve exact HTTPS asset origins observed for the selected account/format, reject userinfo/controls/redirects and enforce byte/deadline/MIME limits. Do not use a broad S3 or HTTPS wildcard. Prefer authenticated same-origin download with a restrictive asset allowlist; do not put private label URLs into public CMS, order emails or logs. Label-asset fetch failure is separate from purchase state. Default PNG avoids introducing conversion behavior in the first slice; additional formats require their own validated retrieval contract.

Buying/printing a label does not mark the order shipped, decrement stock again, create a fulfillment or send a notification. A later explicit “Confirm dispatch” action binds this purchase once, validates order/items and allocation under the order lock, creates the existing fulfillment/shipment linkage atomically, consumes the allocation, and enqueues the existing notification outbox exactly once locally. Actual delivery of email is still at-least-once. Existing offline/manual fulfillment remains available only with allocation-aware quantity validation.

Postage refund/void is a separate future operation and permission, not a Core customer payment refund. Its request needs a fresh idempotency claim, original purchase identity, uncertainty handling and GET reconciliation. Do not delete a purchased record, refund the customer, restock goods, cancel fulfillment or release its shipping allocation merely because a refund request was submitted. A pending void blocks dispatch; rejected/unknown results need review. Release/reuse policy after confirmed refund/void must be carrier-aware and explicitly approved. No refund endpoint is needed to complete the first purchase/reconciliation slice, but the UI must honestly state its absence rather than offer a fake “Cancel label.”

Require existing authenticated admin and ecommerce gates for every public action, with explicit action-scoped audit entries for confirmation, claim, dispatch intent, observed purchase, reconciliation, asset access, credential rebind and later dispatch/void. Public projection exposes only necessary status/cost/tracking metadata; never keys, fences, private snapshot, account identity or raw provider errors. Internal malformed data is sanitized 503, not user-validation 400 with a raw Zod error.

Proposed retention: keep immutable identity/hash/cost/action evidence while the order and operational audit policy require it; retain private snapshots/assets through unresolved purchase/void/review states. Redact private purchase snapshots after a separately approved operational window (starting proposal: 30 days after terminal operational resolution, not merely quote completion). Avoid silently inheriting quote redaction for unresolved labels. Document independent backup retention and deletion behavior. Bounded cleanup must never delete unresolved claims or imply provider cancellation.

5. Populated additive migration, backup/restore and actual runtime restart checks. Older binaries do not understand allocation/purchase fences; prevent mixed writers and unsafe normal downgrade. Extend local evidence inventory with source-pinned opt-in suites; do not relabel quote-only browser acceptance as purchase proof.

Before production, establish billing/adjustment consent, account continuity, provider-specific repeat-purchase/non-purchase semantics and label asset access/retention. This proposal grants no test or production provider call.

Recommended implementation order: contract and additive storage/allocations → bounded buy and GET transports → orchestration/recovery → private asset access → explicit admin purchase UI → allocation-aware dispatch integration. Keep void/refund and production activation separate, visible follow-ups. The Orchestrator owns acceptance and any adjustment to this boundary.
