# Shipping quote persistence foundation

Implements the storage portion of [shipping quotes v1](shipping-quotes-v1.md). This is not a transport, endpoint, carrier readiness or production acceptance claim.

`EcommerceShippingQuotesStorage` requires an explicit `ShippingQuoteTransaction` for every operation. It does not open or commit independent transactions. The future service must acquire credential/provider serialization and order/location locks, check a same-key replay before current eligibility/configuration resolution, prepare the accepted input, claim, commit, then dispatch outside database locks. Storage does not authorize credentials, validate payment/fraud or resolve current order/location data. `replay` and `claim` independently compare the canonical client request hash; conflicting bodies produce a sanitized 409. Concurrent identical claims share one row and original fencing token.

The accepted snapshot parser contains version, order/location identity, sorted item selections, USD, two normalized domestic addresses and one normalized ounces/inches parcel. Address fields are bounded to 200 characters; controls are rejected before trimming, state codes use US states/DC, ZIP is structural, recipient name/company is required, phone/email are not persisted. This does not verify deliverability. Snapshot and client request hashes are distinct; sorting uses code-unit comparisons, independent of process locale. Addresses and server-owned values cannot affect client replay identity.

Claims have a maximum 60-second deadline and 15-minute freshness measured from initial claim. `expirePending` and `get` change elapsed pending attempts to unknown without redispatch or token rotation. Only a matching token may resolve pending/unknown; terminal results cannot be overwritten. An already verified shipment identity cannot be replaced. Completions accept only bounded normalized rate data, safe enumerated errors and test-mode identities. The service must verify provider identity/mode before passing it to storage. Database uniqueness scopes shipment ID to provider and credential generation. No provider reference is treated as uniqueness.

`get` reports time-based staleness; the future service additionally compares current accepted input/generation and returns only the intended sanitized API projection. Storage rows are private internal data, not public response contracts. `redactTerminalSnapshots` clears the entire private snapshot exactly 30 days after completion, retains request/snapshot hashes, order/location/items, provider/generation/shipment identity, normalized cost/rates and status, and never prunes pending/unknown. It is idempotent. Scheduling is future orchestration work; the operation itself exists before workflow activation.

Migration 0065 is additive and replay-safe, registered in the explicit SQL reconciliation runner after 0064. Like adjacent 0062–0064, it does not add a historical Drizzle journal entry. Existing shipments and fulfillments are untouched. The order FK prevents removal of an order with retained quote audit data; location/item identities are retained values rather than cascading references. Future order-deletion/retention policy must explicitly account for audit preservation. Roll forward is preferred; old code cannot process new pending/unknown attempts, and the combined CRM release's stricter rollback policy still applies. Do not drop the table to roll back an application binary.

The opt-in PostgreSQL suite uses `SHIPPING_QUOTES_TEST_DATABASE_URL`, accepting only PostgreSQL protocol, exact loopback `127.0.0.1`, database `core_shipping_quotes_test`, and no URL query/hash. It covers races, replay conflicts, rollback, expiry/fencing, immutable verified identities, exact freshness/retention boundaries, safe normalized inputs, FK/lifecycle restrictions and two full populated migration replays. No transport/provider calls are made. Real provider acceptance, full backup/restore of this new table, orchestration and browser checks remain subsequent gates.
